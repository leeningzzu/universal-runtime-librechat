# Optional Pack lifecycle and staged development

**Protocol only.** Current promotion, installation and activation statuses
must come from the existing Runtime promoted registry, exact installed
projection, Project bindings and current accepted evidence. Candidate
directories alone are not deployed Pack status.

## Roles and independent fact owners

- Core and Project: normal chat, Project memory/history/files, source and
  artifact continuity, fully usable with **zero installed user Packs**.
- Pack: optional coherent domain capability. Never Project identity.
- Skill: narrow reusable method; use LibreChat native Skill support,
  permissions, authoring and reuse, not a parallel generic Skill engine.
- Provider: model access/profile only, not Project or Pack identity.
- Runtime: permission, promotion, pinned revisions and lifecycle audit,
  not a second User Shell.
- MCP/local action: optional interoperability and replaceable machine
  capability, not an alternate governance plane.

## Exact lifecycle

Candidate → independent positive/negative/held-out review → explicit
Promotion → optional Install → explicit Project bind/Activate → pinned
Job revision → Deactivate/Unbind → optional Uninstall → guarded update or
rollback.

Promotion does not install; installation does not activate; deactivation
does not uninstall. An update must not rewrite historical pinned Jobs
or automatically adopt a Project. Default is one Primary Pack per
Pack-governed Job. Generic multi-Pack orchestration stays deferred.

A Project fact stays Project Source/Memory/Artifact. A Project-specific
method may become a local Overlay. A Skill Candidate needs an independent
reuse consumer plus positive/negative/held-out with-vs-without evidence.
A Domain Pack needs coherent domain capability; a Universal Pack requires
materially different independent domains and held-out value proof.

## Product sequencing

1. Keep Packless Core and Project continuity usable first.
2. Academic Paper: reconcile promoted and installed exact revisions, user
   Project binding, natural-use evidence and permissions before updating.
3. Novel → review/report → market/stock analysis: consume existing
   candidates and native Skills one coherent domain capability at a time.
4. Publish a Pack only after separate permission, provenance, privacy and
   held-out value review. No silent Promotion, Install or activation.

The source-only Git repository intentionally excludes unreviewed domain
Packs and private Project content. Program-level representative Pack
formation and completeness are not proved by the existence of Pack code.
