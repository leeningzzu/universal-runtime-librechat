# 安全、个人信息与本地清理准则（R241 候选）

## 需要区别的对象
1. 发行包内 bytes：当前 81 个源文件，签名前必须检查固定镜像来源、源文件完整性及私人数据意外进入的情况。
2. 用户首次安装以后创建的数据：账号、个人模型 API Key、Project、Chat、Memory、Library、File、Source 和上传附件。默认不得复制开发机旧数据。
3. Developer 机器 Production 与历史归档：原有 Project、Mongo、持久化卷、C5 保护备份、回滚证据、旧可选 Pack 和当前工作区，不属于可自动清除的缓存。
4. 临时可再生测试材料：只在当前作业确切归属、无人使用、可重建且通过使用者数据保护检查后，在其天然 closeout 清理。

## 本候选的明确边界
- 当前选定 payload 的敏感规则扫描没有发现模型密钥、PEM 私钥、开发机 Windows 用户根路径、旧 Pack 执行器；不能据此声称整个 Docker 镜像历史层、第三方包及全部 Git 历史完成隐私和许可证扫描。
- 本地旧开发 main 的六个被追踪文件出现 Windows 用户路径；它仍留在本地，只允许隔离清洁发行分支作为待审发布对象。不要以 git push --all 或 --mirror 发布历史内容。
- 当前编译后的 EXE 没有带入真实用户账号、测试 Project、用户资料或生产 Mongo/上传卷；但是新版运行以后用户创建的信息应在私人存储中持久保存。
- 卸载默认保留个人数据；如果将来需要“卸载并清除全部个人数据”，必须给用户明确二次选择、确认所有权和备份策略，绝不对其他程序的 Docker 卷使用 prune、down -v 或递归删除整个数据根。
- 已证明不再使用的测试文件可清理；不得按文件名中的 old、backup、stage、cache 盲删，也不得仅凭 EXE 生成就删除 Git 源码或唯一的构建、回滚材料。

## 公共 GitHub 发布前必需
- 公开/私有仓库目标、Owner、允许的发布分支和权限边界由账号持有人确认；
- 对候选全部源文件、依赖许可证/漏洞、编译第三方素材和 Docker 镜像每层历史做独立审计；
- GitHub 中代码的提交哈希、CI 工件 SHA、签名 EXE SHA 与被安装的逐文件 SHA 形成完整链条；
- 源码先在 GitHub 验证可恢复后，才能评估哪些本地 Staging 与非保护性临时产物可以退役。
