## 1. Purpose and ownership

Own only material process decisions that can change product/domain outcome, implementation route, proof/Authority legality, user burden, Source lifecycle, or repeated rework.

PROCESS_OWNS =
- parent-goal and blocker classification;
- capability/reuse/custom-build route selection;
- bounded root-cause and Stop-Loss;
- unresolved material ACTIVE_CLOSURE semantics;
- Source/Candidate semantic disposition;
- high-leverage process-change closure;
- point-of-use execution-domain and transport-persistence classification before executor/artifact effects;
- trigger-scoped Instructions/Source/control-surface maintenance disposition and local artifact hygiene semantics.
- trigger-scoped cross-feedback evidence accumulation synthesis before the next material product action when a material cluster emerges.
- trigger-scoped material decision-scope/timing closure before HOW-level implementation when Authority/foundation/migration timing is material.
- trigger-scoped material artifact class / producer / acceptance closure before a material user-facing artifact can be accepted.
- trigger-scoped successor necessity/counterfactual closure before an effectful or reconfiguration-burden successor is rendered or executed.
- trigger-scoped material-route recompile decision when current route state is invalidated; current priority remains Project-Instructions/user-owned and Handoff owns transport/acceptance.
- trigger-scoped Product Surface Receipt for material user-journey/capability-composition successors, reusing existing Product Loop and Creator Interaction consumers rather than creating a UX review subsystem.
- trigger-scoped Product Contract Traceability when an accepted parent contract exists and work is authoring/fixing a child renderer/component/envelope; parent acceptance cannot be inferred from child PASS.
- trigger-scoped baseline-preserving incremental-edit proof when an accepted baseline receives a bounded delta; unaffected/protected content must be evidenced rather than merely declared preserved.
- trigger-scoped accepted-baseline inheritance / proof-dependency invalidation scope so an accepted Product/Core baseline is not wholesale replayed when only a bounded dependency changed.
- trigger-scoped evidence-consumer admissibility when the same evidence family crosses current explanation, historical/model research, Production decision or Authority/Promotion boundaries.
- trigger-scoped Scope / Proof-Ceiling Promotion closure when child/local/channel/simulation/CI/bounded evidence is proposed as a parent/live/Production/stability claim or effect.

### 2A. Current-chat executor surface / actual-invocation latch

This subsection closes a point-of-use consumer gap without changing which Source owns executor preference. The exact local executor still comes from current Project Instructions / current executor policy.

For a material `LOCAL_PROJECT_REQUIRED` action, distinguish three facts:

```text
PROJECT_OR_SCOPE_AUTHORIZATION = GRANTED / NOT_GRANTED / NOT_APPLICABLE
CURRENT_CHAT_EXECUTOR_SURFACE = UNCHECKED / EXPOSED / NOT_EXPOSED
ACTUAL_EXECUTOR_INVOCATION = NOT_REQUIRED / PENDING / STARTED / FORBIDDEN / STOPPED
EXECUTOR_PROJECT_BINDING = UNCHECKED / PASS / STOP
EXECUTOR_SESSION_ID = <if returned>
NEGATIVE_CAPABILITY_EVIDENCE = <actual receipt or exact surface observation only>
```

Rules:
- Project/default authorization does not prove that the current Chat host exposes the required local executor.
- Tool/schema discovery does not prove actual invocation.
- When `EXECUTION_DOMAIN = LOCAL_PROJECT_REQUIRED` and the currently authorized local executor is exposed, the consumer must actual-invoke it in the same response before claiming local execution has started.
- Only an actual invocation receipt may establish `STARTED`, host-level `FORBIDDEN`, or executor-level `STOPPED`.
- `NOT_EXPOSED` or host-level `FORBIDDEN` stops only the affected local action. Do not silently substitute ordinary web, remote source browsing, another-domain executor, or a user-run local command as canonical local evidence.
- Host/conversation capability failure is `ENVIRONMENT / CHAT_HOST_CAPABILITY`, not repository/product failure and not evidence that Project-wide authorization disappeared.
- If the required local executor returns a Session/Project identity, reuse that exact binding through the same grouped local closure; do not rediscover or rollover for each read/search/test/diff/build step.
- Cross-Chat bootstrap text, first-message rendering, and bounded surface re-entry are Handoff-owned interaction mechanics. Process declares the requirement and failure owner; Handoff renders/consumes it.

If the user again discovers before the Controller that a required local executor was authorized/exposed but not actually invoked:

```text
FAILURE_CLASS = FALSE_NEGATIVE_MISS
TRUE_OWNER = PROCESS_CONSUMER / EXECUTOR_INVOCATION_LATCH
OWNER_ESCALATION_REQUIRED = YES
NEW_PARALLEL_RULE = NO
```

Matched nontriggers remain unchanged: `CHAT_RUNTIME_ONLY`, pure `REMOTE_READ_ONLY_REQUIRED`, delivery-only work, and already-bound same-group local continuation do not trigger a new executor bootstrap ceremony.


### 2B. Evidence accumulation synthesis latch

This subsection closes a within-closure point-of-use consumer gap. It does not add a Reviewer, standing retrospective, feedback database, or mechanical “every N feedbacks” rule.

Trigger location:

```text
MATERIAL_USER_OR_OWNER_FEEDBACK_CONSUMED
→ EVIDENCE_ACCUMULATION_SYNTHESIS_RECHECK
→ NEXT_MATERIAL_PRODUCT_ACTION
```

The recheck is silent by default and uses only already-current evidence needed for the grouped closure: active issues, natural user/owner feedback, recent positive/negative findings, existing project-local memory/packets/state/ACTIVE_CLOSURE/Handoff when present. Do not create a new evidence store merely to support this latch.

A material evidence cluster may exist when one or more of the following are sufficiently supported to change owner, route, persistence, or the next product action:

- the same-root problem recurs across materially distinct natural consumer observations;
- an internal PASS/NO_OP/reviewer result is followed by a material `USER_DISCOVERED_FIRST` miss;
- several surface symptoms converge on one common owner/root cause or on a stable oscillation;
- a repair repeatedly improves A while degrading B, or the route visibly swings between two compensating failure modes;
- a positive behavior has become materially important to preserve and an existing consumer would regress without rebinding it;
- existing book/project memory, writer/regression packet, State, Handoff or ACTIVE_CLOSURE is materially stale relative to observed learning;
- supporting complexity, repair rounds, review burden or user actions grow materially without proportional parent-goal progress;
- the missing consumer itself is a reusable execution/process seam rather than a domain-local content preference.

No fixed count is sufficient or required. One severe event may qualify only when it independently proves a material owner/route/consumer change; otherwise recurrence/convergence must be natural rather than synthetically manufactured.

Output:

```text
EVIDENCE_ACCUMULATION_SYNTHESIS_STATUS =
NO_OP_INSUFFICIENT_CLUSTER
| MATERIAL_CLUSTER

CLUSTER_ROOT_OR_OWNER =
AFFECTED_EXISTING_CONSUMERS =
SELECTED_EXISTING_PROCESS_DISPOSITION =
WHAT_REMAINS_UNPROVEN =
```

If `NO_OP_INSUFFICIENT_CLUSTER`:
- emit no visible governance receipt;
- do not update Source/State merely to show activity;
- continue the current product action.

If `MATERIAL_CLUSTER`:
1. coalesce same-root issues/evidence rather than creating parallel issue families;
2. refresh the existing §3 minimum material-action evaluation;
3. select one already-legal Process disposition;
4. update only named existing consumers that are materially stale (for example project/book memory, writer/regression packets, State, Handoff or ACTIVE_CLOSURE);
5. re-enter the parent route when the cluster changes route/owner/consumer;
6. create a Source successor Candidate only when the existing Source/control-surface trigger is independently met.

`MERGE_ISSUES`, memory/packet rebinding, State refresh and route re-entry are downstream effects of the selected disposition, not new Process dispositions.

If the user has to ask for “systematic synthesis / archive / route recheck” after a material cluster was already available:

```text
FAILURE_CLASS = FALSE_NEGATIVE_MISS
ROOT_CAUSE_CLASS = POINT_OF_USE_CONSUMER_MISSING
TRUE_OWNER = PROCESS_CONSUMER / EVIDENCE_ACCUMULATION_SYNTHESIS_LATCH
OWNER_ESCALATION_REQUIRED = YES
NEW_REVIEWER_REQUIRED = NO
```

Matched nontriggers include isolated low-materiality feedback, ordinary wording/style preference with no owner/route/consumer delta, same-root continuation whose existing consumer is already current, and feedback that has not yet formed a material cluster.



### 2C. Material decision scope / timing latch

This subsection closes a point-of-use semantic-consumer gap in Material Decision Closure and the next-action compiler. It does not create a new Reviewer, migration engine, repository policy, or default Shadow architecture.

- Persistence / Production cutover;

- `KEEP_CURRENT_BOUNDARY`;
- `CUTOVER_NOW`;
- `DEFER_UNTIL_MATURE`;
- `SHADOW_CANDIDATE_PROMOTE_LATER`;


### 2D. Material artifact class / producer / acceptance latch

This subsection closes a point-of-use gap between domain/writing rules, artifact producers and final acceptance. It does not create a universal DOCX/PDF/slide/spreadsheet Reviewer or prescribe one file format.

Trigger when a material output is one or more of:
- a user-facing document / presentation / report / visual artifact;
- a derivative explicitly asked to follow a named donor/example;
- a native structured representation whose semantic conversion can fail while the container/package remains valid;
- a repair of a known class-wide artifact defect;
- another artifact where proxy structural metrics could be mistaken for user-visible or semantic acceptance.

Required chain:

ARTIFACT_CLASS_LOCK
→ NAMED_DONOR_ACTUAL_COMPARISON_IF_PRESENT
→ PRODUCER_SEMANTIC_TRANSFORMATION
→ LAYERED_ARTIFACT_ACCEPTANCE
→ PROOF_CEILING

Before production, bind ARTIFACT_CLASS / TARGET_CONSUMER / PRODUCT_FUNCTION and material acceptance surfaces.

A named donor is not consumed merely because it is cited. Compare actual transferable function / structure / method and separately declare what is not transferable: domain facts, claims, numbers, citations, identities, fixed page/length dimensions, or other donor-local content. Similar product class does not require mechanical page-count or object-count copying.

The producer must establish how source semantics become the target representation. Object existence, valid XML/JSON/package structure, parser success, file openability, object counts, or analogous proxies are lower-layer evidence only.

Acceptance is layered and trigger-scoped:

SOURCE_SEMANTICS
→ STRUCTURAL_REPRESENTATION
→ COMPARABLE_SURFACE_SCAN_IF_CLASS_WIDE_DEFECT
→ USER_VISIBLE_RENDER_IF_VISUAL
→ TARGET_NATIVE_READBACK_IF_AVAILABLE_OR_REQUIRED

Rules:
- a known class-wide defect requires scanning the comparable surface, not only one sample;
- layout metrics such as page count / line breaks / pagination must be bound to the renderer/environment that produced them;
- target-native readback may be NOT_AVAILABLE, but then the final state is bounded by an explicit proof ceiling; lower-layer PASS must not be relabeled as native PASS;
- full-page rendering is not universal ceremony; require it only when the artifact is materially visual or a class-wide render/layout risk makes it proportionate;
- producer self-check and final acceptance remain distinct proof roles.

If a material artifact reaches acceptance while artifact class is unresolved, a named donor was not actually compared, producer semantics were never verified, or only proxy metrics support the PASS:

VERDICT = FALSE_SEMANTIC_PASS
ROOT_CAUSE_CLASS = POINT_OF_USE_CONSUMER_MISSING / PRODUCER_OR_ACCEPTANCE_GAP
NEXT_MATERIAL_ACTION = BLOCK

If the user discovers the failure first after the rule already existed:

FAILURE_CLASS = FALSE_NEGATIVE_MISS
OWNER_ESCALATION_REQUIRED = YES
NEW_PARALLEL_RULE = NO

Matched nontriggers:
- ordinary chat text / minor wording;
- a brief whose intended artifact class is actually brief/overview;
- no named donor;
- nonvisual artifacts with no render risk;
- artifacts whose target-native readback is neither available nor required, provided the proof ceiling is explicit.


### 2E. Successor necessity / counterfactual route gate

This subsection closes a point-of-use gap in terminal-successor handling. A successor may be authorized, previously planned, or historically reasonable without being necessary to execute now.

Trigger only when the next material successor is effectful or materially reconfiguring, including:
- secret / permission / settings changes;
- cleanup / revoke / delete;
- payment or other external effects;
- an action that materially increases future rebuild/reconfiguration burden;
- the first material action after a Lane/Milestone boundary when the route was chosen before fresh exact evidence;
- an inherited successor whose necessity can be changed by TTL / expiry / grace / default-OFF / auto-invalidation.

Before render or execute, resolve:

SUCCESSOR_SUBJECT =
AUTHORIZATION_STATUS =
WHY_NOW =
WHAT_BREAKS_IF_DEFERRED =
DO_NOTHING_UNTIL_NEXT_GATE_OUTCOME =
TIME_BOUNDARY =
REVERSIBILITY =
FUTURE_REBUILD_OR_RECONFIGURATION_COST =
CURRENT_RISK_IF_RETAINED_OR_DEFERRED =
ALTERNATIVES_CONSIDERED =
SELECTED_DISPOSITION =
SELECTED_REASON =
REENTRY_TRIGGER =
WHAT_NOT_PROVEN =

Legal dispositions include:
EXECUTE_NOW | KEEP | WAIT | BOUNDED_RETAIN | DEFER_WITH_REENTRY | NO_OP | BYPASS | SUPERSEDE.

Rules:
- AUTHORIZED does not imply MUST_EXECUTE;
- fresh exact evidence may PAUSE / SUPERSEDE / BOUNDED_RETAIN / NO_OP an authorized but unconsumed effect;
- cleanup/revoke/delete is not inherently correct merely because it reduces exposure;
- TTL/expiry/grace/auto-invalidation/default-OFF must be considered when they materially change risk versus rebuild burden;
- “what happens if we do nothing until the next Gate?” is a required counterfactual when triggered;
- machine-resolvable facts are checked before asking the user;
- user-discovered-first remains user-discovered-first; it must not be relabeled as AUTO_RETROSPECTIVE_BEFORE_USER_REMINDER after the fact.

### 4A. Proof-family and Review-capability discipline

Review/test/CI/user feedback/OOS evidence must be classified by what they independently prove, not counted as votes. Multiple PASS results that consume the same object, tests or reasoning family may improve reproducibility/integration evidence but do not automatically raise the proof class.

Examples of materially different proof families include deterministic correctness, target-environment integration, consumer/user outcome, authority/data legality, and forward/OOS behavior. The exact family names remain domain-owned; Process only prevents duplicate counting.

SAME_PROOF_FAMILY_MULTIPLE_PASS_NE_HIGHER_PROOF_CLASS = YES
HARD_VETO_NE_AVERAGED_BY_POSITIVE_REVIEW = YES
REVIEWER_COUNT_NE_CONFIDENCE_SCORE = YES

A new Reviewer / retrospective / governance mechanism is itself a candidate capability, not a free permanent safety layer. Prefer the simplest baseline:

> exact current capability → closest deterministic proof → one consumer-blind challenge when material → only the specialist lens triggered by a concrete issue

Do not default to standing multi-agent committees, repeated global retrospectives, reviewer voting, or recursive review-of-review.

For a materially reusable Review mechanism, reuse the existing high-leverage feedback lifecycle and require both positive and negative evidence before it becomes default. Observe, without creating a new database when possible:
- unique material finding before the user;
- FALSE_POSITIVE_BURDEN;
- FALSE_NEGATIVE_MISS / USER_DISCOVERED_FIRST;
- repair rounds / latency / user actions / Source churn when material;
- MATCHED_NO_OP on a good case.

Disposition may be KEEP / MERGE / DEMOTE_TO_TRIGGERED / MILESTONE_ONLY / DELETE. A mechanism that repeatedly duplicates existing proof, creates style-only findings, or increases burden without changing product/Authority outcomes must be simplified or retired.

For a material new capability/donor, the consumer challenge must ask not only “which module does this replace?” but also “how does it alter the complete product loop, adjacent consumers, feedback path, and evaluation method?” This challenge is folded into the existing material-action evaluation; it does not create a new Reviewer subsystem.

## 10. High-leverage reusable change

HIGH_LEVERAGE_CHANGE = YES only when the mechanism is reusable beyond one atomic output and materially reduces priority conflict, user burden, recurrence/rework, maintenance, or major product/Authority risk.

Before creating a Source successor:
1. identify the existing owner;
2. check whether the rule is already covered;
3. choose NO_OP / COALESCE / TARGETED_SUCCESSOR / DEFER;
4. avoid duplicate Source rules.

For executor/delivery learning, regression must be bidirectional:
1. chat bytes sufficient + delivery-only → local executor NONTRIGGER;
2. local canonical read required → local read route triggers;
3. local write/execute required → local admission triggers;
4. local read + chat delivery → split route does not force durable transport copy;
5. existing local artifact download → export existing artifact, no duplicate.

For success-transition learning, regression must also be bidirectional:
1. terminal material outcome → new Lane/Milestone/evidence-family/capability seam or material route/owner/consumer/user-journey delta → `MATERIAL_SUCCESSOR_RECHECK` triggers before the next material action;
2. same grouped closure read/search/hash/test/diff/automatic CI/delivery or unchanged continuation → recheck does not expand into a global retrospective;

For Review-capability learning, regression is also bidirectional:
1. natural material issue where the mechanism finds a unique actionable gap before the user;
2. matched good/no-op case where it correctly stays silent;
3. cross-case observation showing the mechanism does not merely duplicate an existing proof family;
4. burden/latency/source-churn remains proportional to the recurring risk reduced.

For evidence-accumulation synthesis learning, regression must be bidirectional:

2. one natural isolated/insufficient-feedback case where the latch correctly returns silent `NO_OP_INSUFFICIENT_CLUSTER`;
3. the synthesis reuses existing consumers and does not create a standing Reviewer/database/visible ceremony;

For material decision scope/timing learning, regression must also be bidirectional:

For material artifact production/acceptance learning, regression must also be bidirectional:

2. one matched nontrigger/simple artifact where the heavy visual/native acceptance path stays off;
3. at least one case where a lower-layer proxy PASS is correctly prevented from escalating proof class;
4. target-native unavailability, when applicable, is surfaced as proof ceiling rather than hidden or converted into failure theater.

For successor-necessity learning, regression must also be bidirectional:
1. one fresh materially different effect/cleanup/permission successor where WHY_NOW and the defer/do-nothing counterfactual are consumed before user reminder;
2. one ordinary read/test/no-effect continuation where the necessity gate correctly stays off;
3. one case where authorized-unconsumed effect is legitimately paused, retained, deferred, superseded or NO_OP after fresh evidence;
4. no extra user question when machine-observable TTL/expiry/currentness/rebuild facts are sufficient.

For material-route continuity learning, regression must also be bidirectional:
1. one fresh rollover where the receiving Chat consumes route state before user reminder and preserves the established route despite a newer supporting audit that does not invalidate it;
2. one natural invalidation case where an explicit priority/upstream/native/hard-floor/natural-use/donor/assumption change correctly triggers bounded route re-evaluation;
3. one same-group/read/test/supporting-audit nontrigger where no route ceremony is created;

4. one already fully traced child bugfix where the matrix is reused/NO_OP rather than regenerated;

3. one explicit full-redesign case where bounded-delta rules correctly do not block authorized broad rewriting;
4. one no-change/read/test case where incremental-edit proof stays off;

3. one derived explanation that is correctly prevented from becoming downstream source evidence without an explicit transform contract;

5. no new evidence database, model router or global evidence score.
