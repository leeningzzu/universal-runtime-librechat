# Aides roadmap — user-value sequence

This is a **sanitized public planning contract**, not the current Windows Build Status or a Product/Program PASS declaration. Actual Stage, exact run and unique next action belong only to the latest accepted Handoff/Build Status and newer machine evidence. Already accepted scopes are inherited, not replayed.

## P1 — Complete Project experience (current parent product priority)

Deliver one normal-user journey: New Project -> purpose once if needed -> New Chat -> direct request -> reuse **owned Project** Instructions/Memory/Files/Sources and exact older-chat recovery -> show traceable evidence -> save durable Source/Artifact -> reopen/continue. Preserve strict Project scope, no full history injection and no cross-user leakage.

Close only genuine remaining Project user gaps: current Daily source-to-new-Chat consumption, native file reuse, durable local file bytes, controlled relevant context, Project Archive/Delete retention, same-machine backup/repair and safe error/rollback. Reuse native LibreChat; keep unsafe File Search/RAG off until owner-scope security is proven. Never split each component failure into a new Program Lane.

## P2 — Compose LibreChat native advantages

Preserve one shell with user-selectable Providers/models, Agents, Skills, MCP, tools, connectors and optional local actions. Reuse upstream solutions at the current consumer; no generic duplicate platforms. Zero Packs remains a complete Core use case.

## P3 — User-creatable, optional governed Packs (Aides differentiation)

Reuse the existing Pack Creation and Pack Lifecycle Protocols and native Skills. A Project method may remain Project-local Overlay; a reusable Skill/Domain/Universal Pack Candidate requires the appropriate independent use and evidence. The user can create/review a Candidate, explicitly Promote, then optionally Install, Activate, Deactivate, Uninstall and Update, with exact revision pins and rollback. No automatic Promotion/installation/activation and no generic Pack-factory engine by default.

Prioritize one representative end-to-end user-created Pack with a real independent consumer; broader Domain/Universal expansion only after demonstrated value.

## P4 — Windows EXE installation and lifecycle (final packaging)

After the current Project and representative optional Pack value is usable, reuse mature Windows packaging, install/first-run, startup, repair/update/rollback/uninstall paths. Validate a **fresh EXE installation on a different supported Windows PC** with a new local Project and Packless normal use. No manual Docker/PowerShell/ports or external cloud-sync prerequisite. Test product code/data separation and preservation on same-PC update/repair; importing an old Project from another machine is a separate optional journey.

EXE packaging is not blocked by absence of a default installed Pack, and no optional Pack payload may be preinstalled in a fresh consumer shell. The optional Pack creation stage is product sequencing, not a hidden technical dependency for Packless startup.

## Parallel safety and release controls (not standalone substitute product work)

Local data integrity, owner isolation, permissions, secrets, secure File Search default-off, recoverability, upstream/license currentness, GitHub PR + required CI, and clean release/source provenance remain hard floors at their actual consumers. Do not infer Product PASS from a candidate build or a green CI badge. Do not make cross-computer migration, a cloud storage service, or custom installer engine a new prerequisite.

Product PASS and Program PASS each require their own explicit completeness receipt, not this roadmap.
